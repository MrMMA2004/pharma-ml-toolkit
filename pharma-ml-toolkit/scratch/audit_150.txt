FINDING 1 (RISK — docstring lies; the promised typed guard is dead code)
  File: src/pharmaml/ml/training.py, lines 601-607 (docstring) vs 684-688 + 711-713.
  What: benchmark_feature_families' Raises section promises ModelError when
        "the dataset has fewer aligned rows than cv folds". The only check for
        that condition (``if len(aligned_y) < cv: raise ModelError(...)``,
        lines 684-688) lives INSIDE the per-family ``try:`` whose blanket
        ``except Exception`` (line 711) converts every raise — ModelError
        included, it subclasses Exception via PharmaMLError — into a NaN board
        row plus a log warning. The promised error can never propagate.
  Why it matters: a too-small dataset (e.g. 2 molecules, cv=3) returns an
        all-NaN leaderboard instead of the actionable ModelError — the exact
        "100%-NaN leaderboard" degradation the sibling compare_models guards
        against UP FRONT (training.py:411-421, the 27-A fix), whose docstring
        wording was copied here. The two siblings' documented contracts
        disagree with their behaviour. No test pins the raise (there is nothing
        to pin — it never fires).
  Fix sketch (minimal): hoist a dataset-level guard before the family loop,
        mirroring compare_models:
            if isinstance(cv, int) and len(y_series) < cv:
                raise ModelError(f"cv={cv} folds exceeds the number of aligned "
                                 f"rows (n={len(y_series)}) ...")
        and keep the in-loop aligned-rows check as the honest per-family NaN
        path (a family that drops molecules below cv). Delete or reword the
        docstring clause if the swallow is the intended behaviour.

FINDING 2 (RISK — raw OverflowError from the float|None|NaN contract; probed)
  File: src/pharmaml/chem/converters.py, line 288 (``return 10.0 ** (exponents[unit_key] - value)``).
  What: for a FINITE pIC50 below ≈ -299.2547 (nM) / -296.2547 (pM) /
        -308.2547 (M) the exponent exceeds log10(DBL_MAX)=308.2547 and CPython
        float ``**`` raises ``OverflowError: (34, 'Numerical result out of
        range')`` — a raw traceback out of a function whose contract is
        "float, None (unparseable) or NaN". The docstring handles None/NaN/
        ±inf (lines 275-287) but not finite overflow. PROBED (scratch/
        probe_audit_150.py): 10.0**(9-(-299.25)) = 1.78e308 fine;
        10.0**(9-(-299.26)) -> OverflowError; 10.0**(9-(-300)) -> OverflowError.
        The underflow direction is silent: 10.0**(9-400) = 0.0 (see observation
        O2). The blast radius includes ic50_from_pic50_series and
        add_ic50_column — ONE absurd cell in a prediction sheet kills the whole
        conversion job with a raw traceback (add_ic50_column's worker runs it
        bare, playground.py:14747).
  Why it matters: the audit bar counts "guard gaps that crash with raw
        tracebacks instead of typed errors". Reachability is narrow but real:
        (a) a directly supplied pIC50 ≤ -299.26 (hand-entered value, dirty
        join, another pipeline's unbounded output); (b) the extreme round
        trip — the probe shows ic50_to_pic50 of an IC50 at DBL_MAX (a
        parseable finite value) emits pIC50 ≈ -299.2547/-296.2547/-308.2547,
        and the exact-boundary reverse pow OVERFLOWS for M, nM AND pM units.
        The existing round-trip test only covers pIC50 0.5-11.2.
  Fix sketch (minimal): decide the honest out-of-range answer and pin it —
        either
            try:
                return 10.0 ** (exponents[unit_key] - value)
            except OverflowError:
                return float("inf")   # the mathematical limit, passes no-skill triage
        or return NaN (the module's own "no honest concentration" convention,
        same cell the ±inf branch uses). Either way add the boundary to
        TestPic50ToIc50 and one line to the docstring's Returns/Notes.

FINDING 3 (POLISH — silent column clobber; the round-146 guard precedent
           stopped one function short)
  File: src/pharmaml/chem/converters.py, lines 298-350 (add_ic50_column).
  What: out_col is never validated. ``add_ic50_column(frame, pic50_col="pIC50",
        out_col="pIC50")`` computes from the original column then silently
        REPLACES it with IC50 values (the user loses the pIC50 column);
        ``out_col="SMILES"`` destroys the SMILES column the same way. No
        warning, no error. Round-146's FIX 3 added exactly this guard to
        prepare_pic50_dataset (converters.py:585-594, refusing out_col in the
        three reserved result columns, pinned by
        test_out_col_collision_with_reserved_columns_refused) but the two
        add_*_column twins were left without it — the module's own guard
        convention is now inconsistent across three sibling functions
        (add_pic50_column, lines 175-217, shares the gap; pre-round-31, listed
        for context only).
  Why it matters: silent data loss on a caller typo — the same defect class
        the project itself chose to fix in round 146.
  Fix sketch (minimal): next to require_columns, refuse the collision (at
        minimum the self-clobber, ideally any existing column — the forward
        twin's contract is "append", never overwrite):
            if out_col == pic50_col or out_col in frame.columns:
                raise DataValidationError(
                    f"out_col {out_col!r} already exists in the frame -- pick a "
                    "fresh column name (add_ic50_column appends, never overwrites)"
                )
        (match prepare_pic50_dataset's style; mirror onto add_pic50_column in
        the same change or leave that for its own round, as you prefer).
