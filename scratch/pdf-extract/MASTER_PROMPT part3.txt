19. CROSS-VALIDATION RESULTS FOR ALL ML AND DL MODELS

19.1. Primary Objective

Extend the results section so that every evaluated machine learning and deep learning model
reports its Cross-Validation (CV) performance.

Cross-validation must be treated as a first-class model evaluation result rather than an optional
or hidden training detail.

19.2. Required CV Information

For every evaluated model, record:

- Cross-validation strategy.
- Number of folds.
- Random seed.
- Individual fold scores.
- Mean CV score.
- Standard deviation of CV scores.
- Training scores where appropriate.
- Validation scores.
- Selected evaluation metrics.
- Best hyperparameters, where applicable.
- Total CV execution time.

Present mean and standard deviation in a clear format:

"CV Score = Mean ± Standard Deviation"

For example, use a clearly labeled format such as:

"0.923 ± 0.018 (5-fold CV)"

Only display actual computed values. This numerical example is illustrative and must never be
treated as a project result.

19.3. Appropriate CV Strategies

Select the cross-validation method according to the problem.

For classification:

- StratifiedKFold.
- StratifiedGroupKFold when group separation is necessary.

For regression:

- KFold.
- GroupKFold when repeated groups or related samples could create leakage.

For molecular datasets:

- Evaluate molecular scaffold-based splitting when the objective is generalization to structurally
distinct compounds.
- Consider grouping molecules by Bemis–Murcko scaffold.

- Avoid placing closely related compounds in both training and validation folds when this would
produce an unrealistically optimistic estimate.
- Document the chosen splitting strategy and its limitations.

Provide configurable fold counts, with reasonable defaults based on dataset size and
computational resources.

Use 5-fold CV when appropriate and feasible. Consider 3-fold CV for computationally expensive
models or limited datasets, and justify the choice.

19.4. Classification Metrics

Include relevant CV metrics such as:

- Accuracy.
- Balanced Accuracy.
- Precision.
- Recall.
- F1-score.
- Macro F1.
- Weighted F1.
- ROC-AUC where appropriate.
- PR-AUC where appropriate.
- Log Loss where probabilities are available.

For multiclass classification, specify the averaging strategy and appropriate ROC-AUC
configuration.

Do not report metrics that cannot be meaningfully calculated for the relevant model or split.

19.5. Regression Metrics

Include relevant CV metrics such as:

- R².
- RMSE.
- MAE.
- MSE.
- Median Absolute Error where appropriate.

Clearly identify whether lower or higher values indicate better performance.

19.6. Deep Learning Cross-Validation

Apply CV to DL models as well as traditional ML models.

For each fold:

1. Initialize a fresh model.
2. Initialize its optimizer and learning-rate scheduler.
3. Train using only the corresponding training partition.
4. Evaluate on that fold's validation partition.

5. Record fold-specific metrics.
6. Preserve reproducibility using appropriate random seeds.

Do not reuse trained model weights across folds unless the evaluation protocol explicitly
requires it and the resulting methodology is justified.

Account for the computational cost of DL cross-validation.

Allow users to select fold counts and computational budgets.

19.7. Prevent Data Leakage

This is a critical requirement.

- Fit imputation, scaling, feature selection, dimensionality reduction, and other learned
preprocessing steps only on the training portion of each fold.
- Use appropriate pipelines.
- Do not use test-set information during hyperparameter selection.
- Keep the final independent test set untouched until final evaluation.
- Use nested CV when an unbiased estimate of the entire hyperparameter selection process is
required and computationally feasible.
- Clearly distinguish hyperparameter-search CV results from independent final test results.

Never label a single validation score as cross-validation.

19.8. Results Interface

Extend the ML and DL results pages with a dedicated CV section.

Include:

- Model name.
- Task type.
- CV strategy.
- Number of folds.
- CV mean.
- CV standard deviation.
- Individual fold metrics.
- Independent test metrics.
- Best hyperparameters.
- Training duration.

Provide sorting and filtering by CV performance.

Display CV results in both tables and interactive visualizations where appropriate.

Recommended charts:

- Model CV comparison.
- Fold-by-fold performance.
- CV mean with standard deviation.
- ML versus DL performance comparison.

- CV versus independent test performance.
- Model stability comparison.

Keep CV performance and independent test performance visually distinct.

19.9. Persistent CV Results

Save CV results in the appropriate project output and database structures.

Preserve:

- Model identifier.
- Dataset identifier.
- Dataset version or fingerprint.
- Feature configuration.
- CV strategy.
- Fold results.
- Aggregated metrics.
- Hyperparameter configuration.
- Execution metadata.

Ensure that CV results can be compared across experiments without accidentally mixing results
from different datasets or preprocessing configurations.

20. PAUSE, RESUME, STOP, AND CHECKPOINT MANAGEMENT

20.1. Primary Objective

Introduce intelligent execution controls for long-running operations.

The GUI must provide appropriate controls for pausing, resuming, stopping, and recovering
computational tasks.

This functionality must be connected to the actual backend execution engine.

A visual Pause button without real execution-state control is unacceptable.

20.2. Job Control Interface

Provide a dedicated control area for long-running operations.

Use the following control states:

RUNNING

- Display a Pause control when safe pausing is supported.
- Display a Stop/Cancel control.

PAUSED

- Display a Resume control.
- Display the saved checkpoint information.
- Allow the user to terminate the paused job if necessary.

STOPPING

- Display the current shutdown or checkpoint operation.

COMPLETED

- Display the final results and available output files.

CANCELLED / INTERRUPTED

- Display the saved progress and whether resuming is supported.

Use clear status indicators, progress bars, elapsed time, and execution logs.

20.3. Safe Pause and Resume

For jobs that support safe pausing:

1. Receive the pause request.
2. Complete the current safe computational unit.
3. Save the execution state.

4. Save the current progress and generated outputs.
5. Verify that the checkpoint has been written successfully.
6. Transition the job into the PAUSED state.
7. Allow the application to close without losing the checkpoint.
8. Restore the job during a later application session.
9. Resume execution from the last verified checkpoint.

The resumed job must continue from the saved position rather than starting again.

20.4. Checkpoint Contents

Save all state required for a valid continuation, as appropriate to the task.

For deep learning:

- Model state.
- Optimizer state.
- Learning-rate scheduler state.
- Epoch.
- Batch or step position where safely resumable.
- Early-stopping state.
- Mixed-precision scaler state where applicable.
- Random-number generator states.
- Training configuration.
- Dataset and split identifiers.

- Completed metrics.
- Training history.

For hyperparameter optimization:

- Completed trials.
- Best parameters.
- Best objective value.
- Optimization history.
- Trial states.
- Current optimization configuration.
- Persistent Optuna study information when applicable.

For cross-validation:

- Completed folds.
- Current fold.
- Completed fold metrics.
- Model and preprocessing state where safe continuation is supported.
- CV configuration.

For generative workflows:

- Completed generation batches.
- Previously generated candidate molecules.

- Model checkpoint.
- Current generation configuration.
- Random-number generator states.
- Filtering and selection progress.

For data processing:

- Completed processing stages.
- Current processing stage.
- Processed output files.
- Data fingerprints and configuration.
- Safe resumption position.

Do not assume that every algorithm exposes a complete resumable state.

20.5. Atomic and Verified Checkpointing

Checkpoint files must be written safely.

- Write to a temporary file first.
- Validate the checkpoint.
- Atomically replace the previous checkpoint only after successful writing.
- Preserve the previous valid checkpoint until the replacement has been verified.
- Record the checkpoint timestamp and job identifier.
- Maintain a compatible checkpoint format version.

- Include configuration and dataset fingerprints.
- Detect incompatible checkpoints before attempting to resume.

For security, do not load untrusted or potentially malicious serialized checkpoints.

Do not rely exclusively on saving model weights when complete training-state restoration is
required.

20.6. Behavior When a Job Cannot Be Paused

Not every computational task supports safe suspension and restoration.

For such tasks:

- Do not pretend that they can be paused.
- Do not introduce an unsafe interruption mechanism.
- Use a Stop/Cancel control instead of Pause.
- Stop at the earliest safe execution boundary.
- Save completed outputs and useful intermediate results.
- Preserve logs and metadata.
- Clearly mark the operation as cancelled or interrupted.
- Terminate the relevant computation cleanly.
- Release resources and background workers.
- Never leave an unintended computation running.

If safe resumption is impossible, start a new execution when the user explicitly requests it.

Never claim that an interrupted job can continue from its previous exact state unless a valid
restorable checkpoint exists.

20.7. Cross-Session Job Recovery

When the application starts:

- Detect incomplete jobs.
- Locate available checkpoints.
- Validate the associated configuration and data.
- Display recoverable jobs.
- Show the last saved progress.
- Allow the user to resume compatible jobs.
- Identify jobs that cannot be restored.
- Avoid automatically resuming incompatible or potentially unsafe jobs.

Maintain a persistent job registry containing:

- Job identifier.
- Job name.
- Operation type.
- Creation time.
- Last checkpoint time.
- Execution status.
- Progress percentage where meaningful.

- Checkpoint location.
- Resumability status.
- Relevant dataset and configuration identifiers.

20.8. Pause/Resume Acceptance Criteria

- [ ] Running jobs expose appropriate execution controls.
- [ ] Safely pausable jobs can be paused.
- [ ] Checkpoints are saved and validated.
- [ ] Paused jobs can resume from the saved state.
- [ ] Cross-session recovery works where supported.
- [ ] Non-pausable jobs expose Stop/Cancel instead.
- [ ] Non-pausable jobs terminate cleanly.
- [ ] Completed outputs are preserved.
- [ ] Interrupted jobs are accurately identified.
- [ ] No false claims of resumability are made.
- [ ] Previous valid checkpoints are protected against failed writes.
