9.1 Before Modifications

- Identify existing user modifications.

PART IV — STRUCTURED MULTI-PHASE EXECUTION

10. MULTI-PHASE WORKLOAD MANAGEMENT AND CONTINUOUS PROGRESS

If the overall workload is too large, complex, or resource-intensive to complete reliably in a
single execution session, divide it into a structured, sequential, and manageable multi-phase
project.

Do not sacrifice inspection quality, implementation accuracy, or verification completeness
merely to finish everything in one session.

10.1 Workload Assessment

Before execution:

- Assess the total workload and technical complexity.
- Identify the number of files, repositories, database components, modules, and integrations
requiring inspection.
- Identify dependencies between tasks.

- Divide the work into logically independent and manageable phases.
- Establish clear objectives and completion criteria for every phase.
- Prioritize tasks based on dependencies, importance, risk, and impact.
- Identify tasks that can safely be performed independently.

Do not load or process every resource simultaneously when incremental inspection would be
more reliable.

10.2 Recommended Execution Phases

Organize the work into the following stages, adjusting the boundaries according to actual
workload:

Phase 1 — Resource Discovery

Inventory all accessible uploaded files, GitHub repositories, project directories, and relevant
resources.

Phase 2 — Detailed Resource Inspection

Inspect individual files and repositories, extract relevant functionality, and document technical
dependencies.

Phase 3 — Database Audit

Examine database architecture, tables, records, relationships, metadata, and data consistency.

Phase 4 — Cross-Reference and Reconciliation

Compare uploaded files and GitHub repositories against database contents. Identify missing
information, discrepancies, and duplicate functionality.

Phase 5 — Playground Audit

Inspect "playground.py", its dependencies, execution paths, and existing feature coverage.

Phase 6 — Gap Analysis

Identify missing, incomplete, redundant, incompatible, or incorrectly integrated functionality.

Phase 7 — Implementation

Complete necessary integrations and modifications incrementally while preserving existing
project functionality.

Phase 8 — Testing and Verification

Perform unit, integration, database, regression, and execution tests.

Phase 9 — Final Reconciliation

Recheck every relevant resource against the final implementation and generate the final
traceability and coverage reports.

Phase 10 — GitHub Backup Verification

Verify that all authorized project components, final implementation changes, and reports are
safely stored in the remote repository.

Adjust the number and boundaries of phases according to actual workload. Do not force
unnecessary stages or combine unrelated tasks merely for convenience.

10.3 Progress Tracking

Maintain a structured execution log throughout the project.

For each phase, record:

- Phase name and objective.
- Completed tasks.
- Files and resources inspected.
- Resources not yet inspected.
- Important findings and discrepancies.
- Database tables or components examined.
- Implementation changes.
- Tests performed and their actual results.
- Unresolved issues and dependencies.
- Current completion status.
- Exact next steps.

When appropriate and authorized, maintain a persistent progress file named:

"PROJECT_AUDIT_PROGRESS.md"

This file must function as a reliable checkpoint, allowing work to resume in another execution
session without repeating completed work or losing important findings.

Use explicit status labels:

- "NOT STARTED"
- "IN PROGRESS"
- "COMPLETED"
- "PARTIALLY COMPLETED"
- "BLOCKED"
- "VERIFICATION REQUIRED"

Never mark a task complete until its completion has been verified.

10.4 Session Handoffs and Recovery

If the task cannot be completed in the current execution session:

1. Finish the current safe and logically complete unit of work.
2. Save relevant findings, intermediate results, and progress records.
3. Document the current project state and completed milestones.
4. Identify the exact next incomplete phase and remaining tasks.

5. Record relevant file paths, repository references, database tables, and implementation
locations.
6. Document unresolved issues, constraints, and dependencies.
7. Provide a concise handoff summary that another session can use to continue the task.

When resuming:

- Read the latest progress checkpoint first.
- Verify that the recorded project state is still accurate.
- Check whether files, database records, or repositories have changed.
- Continue from the last verified milestone.
- Avoid repeating completed inspections unless new evidence or changes make reinspection
necessary.
- Preserve all previous findings and progress.

10.5 Quality and Execution Control

- Never mark an entire phase complete if some required work remains unfinished.
- Distinguish between completed, partially completed, blocked, and unverified tasks.
- Do not skip difficult resources simply because they require additional effort.
- Do not implement features before their requirements and dependencies have been adequately
examined.
- Reconcile discoveries made in later phases with earlier conclusions.
- Use parallel execution only when tasks are genuinely independent and concurrency is safe.
- Avoid redundant tool calls and repeated analysis.
- Do not compromise data integrity or verification quality to accelerate execution.

Important: Multi-phase execution is a method of preserving quality and continuity, not an excuse
to stop after producing a plan.

Complete as much substantive work as possible in each execution session, maintain accurate
checkpoints, and make the next steps explicit.

Golden Rule: Divide large workloads into manageable phases, complete and verify each phase,
preserve progress, and resume exactly where the previous session stopped. Never confuse a
planned task with a completed task.
