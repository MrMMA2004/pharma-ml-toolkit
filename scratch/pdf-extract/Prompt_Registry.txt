1. Purpose and Method
This document is the companion to the GitHub Link Registry: the complete register of every prompt and
instruction the project owner gave across the PharmaML Toolkit sessions. Where the Link Registry captured the
repositories named in those instructions, this one captures the instructions themselves - the actual words, quoted
verbatim wherever the records preserved them, in chronological order, with the round or release each one arrived
in and what it produced.
The register was reconstructed from the project's audited records: the per-round worklog entries, which open with
the task as commissioned, and the toolkit CHANGELOG, which preserves the instruction quotes verbatim at each
release. Entries marked as paraphrases are the ones the records preserved as faithful summaries rather than
verbatim quotes; every other entry is quoted exactly as recorded. Recurring prompts are quoted once in the
register and their repeat counts documented in chapter 4, so the register holds one entry per distinct instruction
rather than one per instance.
The corpus tells one continuous story: an uploaded archive of research scripts became a versioned Python
package, then a tested engineering project, then a 31,105-line graphical application, then an audited,
GitHub-backed product - each stage commissioned by a specific instruction in this register of fifty-six entries.

5. The MASTER_PROMPT
The capstone of the corpus is the MASTER_PROMPT itself: a 1,359-line, ten-phase commission delivered on 4
November 2026 as an uploaded document. It subsumed everything before it - resource discovery, database
reconciliation, the playground integration, testing, and the GitHub backup infrastructure - into one structured
directive with persistent progress tracking. Its title: Comprehensive Project Audit, Database Reconciliation,
Playground Integration, and GitHub Backup.
The prompt is organized in six parts and twelve numbered sections. Part I commands complete resource discovery
- every uploaded file inspected individually, every GitHub repository examined beyond its README, the project
architecture understood before any modification. Part II commands the deep playground.py audit and the
coverage gap analysis, with every gap reported in a nine-field format from problem description through
verification procedure. Part III sets the engineering standards - minimal code, preserved work, no unnecessary
rollbacks. Part IV mandates the multi-phase execution with progress preserved across sessions. Part V demands
test-driven verification. Part VI specifies the GitHub backup infrastructure in nine subsections, from credential
protection through the backup manifest.

Its sixteen core engineering principles include: inspect everything relevant; understand before modifying;
reconcile before integrating; write the minimum necessary code; preserve existing work; prevent unnecessary
rollbacks; test before declaring success; back up every milestone; protect credentials and sensitive data. Its
ultimate goal: a reliable, maintainable, secure, fully tested and comprehensively integrated application with a
verified relationship between all project resources, the database, and playground.py - maintained as a secure,
recoverable GitHub copy.
The audit it commissioned closed all ten phases with evidence on 4-5 November: the four rollback-lost engines
rebuilt, the orphaned modules adopted and tested, six new playground cards shipped in v1.2.107, and the full
project history pushed to the private backup repository - which then restored the entire workspace after three
further environment rollbacks, exactly as its Part VI intended.

6. Method and Evidence
Every register entry is traceable to its source record: the worklog round entry that opens with the commissioned
task, the CHANGELOG release entry that quotes the instruction verbatim, the round-187 review document, or the
audit's traceability matrix. The method notes below cover the corpus-integrity decisions made while compiling
this register.
Method note

Detail

Verbatim vs. paraphrase

Quotes are reproduced exactly as the records preserve them, including original capitalization and phrasing.
Seven entries exist in the records only as faithful summaries (marked 'recorded as a paraphrase' in the
Given-in column); no wording was invented for them.

Deduplication

Recurring prompts appear once in the register with their instance counts in chapter 4 - the 'Playground.py
content is incomplete' prompt launched twenty-five consecutive rounds but is one instruction.

Persian-named uploads

Two uploaded archive filenames are written in Persian script. ReportLab's text engine cannot shape
Arabic-script letterforms correctly (no joining, no right-to-left ordering), so the register transliterates them - '
[the Persian-named machine-learning codes .rar]' and '[the Persian-named Ali-code .zip]' - rather than risk
corrupted rendering. The original filenames are preserved in the worklog and the upload directory.

Link instructions

The thirteen GitHub link instructions are quoted as one template plus a per-round repository table because
the template is byte-identical across instances; only the repository list and minor suffixes vary. The
companion Link Registry documents the same thirteen rounds from the repository side, with every URL
re-verified against the GitHub API.

Coverage claim

The register claims completeness only over what the records preserve: the worklog, the CHANGELOG, the
round review documents, the audit matrix, and the current session. If an instruction was never recorded, it
cannot be registered - and the project's standing changelog discipline is precisely what makes this corpus
whole.

The prompt corpus is the project's true specification. Every module, test, card, notebook and release in the
shipped v1.2.107 tree traces back to one of the fifty-six entries in this register - and the register, like the toolkit it
describes, is now part of the audited history on GitHub.
