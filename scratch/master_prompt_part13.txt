22. FINAL ACCEPTANCE CRITERIA




The project must not be declared complete merely because CI is green.




Completion requires:




- Current source and documentation agree.

- Previous requirements have been verified.

- No duplicate implementation of completed features.

- Critical backend/frontend bugs are resolved.

- Every supported capability has a verified GUI workflow or documented non-GUI status.

- Scientific methods are validated.

- Frontend user interactions have meaningful test coverage.

- Large computations remain responsive.

- Resource management works correctly.
- Active Learning and selected high-value scientific enhancements are integrated only after
validation.

- The clean Windows installation gate passes.

- Offline execution is verified.

- User data survives upgrades.

- PySide6 is retired only after feature parity.

- A new installer is built from the exact release commit.

- Release artifacts, checksums, SBOM, and provenance are consistent.




Use these status labels:




- PASS

- PARTIAL

- FAIL

- BLOCKED

- NOT APPLICABLE




Do not hide blockers.




Do not confuse implementation with validation.




Do not confuse a successful build with a working product.




Do not add features simply because a GitHub repository exists.




The final goal is a robust, reproducible, offline-capable pharmaceutical research platform with
validated scientific workflows, complete GUI integration, and trustworthy Windows distribution.




Engineering principle: verify first, preserve working systems, prioritize scientific value, fix
evidence-backed defects, and expand the platform only when the improvement is measurable.
